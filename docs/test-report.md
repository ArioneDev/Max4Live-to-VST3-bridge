# P0 test report

Environment: Windows 11 x64, Max 9.2.0 (`F:\Max\Max.exe`, `MaxRT_nocef.exe`),
Ableton Live 12 Suite, Visual Studio 2026 (MSVC 19.51), JUCE 8.0.9,
CMake 4.4.3. Tests run from `D:\m4lb-src` (a junction to the workspace folder),
because JUCE's resource compiler fails on non-ASCII build paths.

## 1. Max loads a third-party VST3 by absolute path

Patch: `[vst~ "C:/Temp/m4lprobe/probe.vst3"]` + `open`.

Result: the plugin's editor window (`AP Timbre Resynth`) appeared, and a
downstream probe plugin received `processBlock` calls (900 blocks in 10 s at
64 frames). Absolute-path loading works; no VST3 folder installation or scan is
needed.

## 2. `[amxd~]` hosts a real device

Patch: `[amxd~ "鈥?Autotuna.amxd"]` + `open`.

Result: a visible window titled `Autotuna` appeared. Device UI and patcher load
correctly.

## 3. Loading `[amxd~]` turns Max's DSP off

Patch: `[amxd~]` (dangling) + `[phasor~] 鈫?[snapshot~] 鈫?[js]` logging to files.

Result: the scheduler kept running (a `[metro]` still fired), but every
`snapshot~` value stayed `0`, and a probe VST3 downstream of `amxd~` received
**zero** `processBlock` calls. Removing `amxd~` restored processing.

Fix: send `start` to `[dac~]` after the device has loaded:

```
[loadbang] 鈫?[delay 2500] 鈫?[start( 鈫?[dac~ 1 2]
```

With that, `snapshot~` values advance (0 鈫?0.10 鈫?0.23 鈫?鈥?鈫?0.98) and a
downstream `[vst~]` receives 1400 blocks in 10 s.

## 4. Transport loopback (no device)

Patch: `[vst~ Out] 鈫?[vst~ In] 鈫?[*~ 0.] 鈫?[dac~]` plus the `start` message.

`M4LBTest.exe MaxRT_nocef.exe loopback.maxpat 40`:

```
launched Max pid=6440
attached (createdByUs=1)
pushed 4096 frames
out ring fill: 5632 (heartbeat=176, underruns=24)
ramp at 0; compared 4096 frames: mismatches=0 maxDiff=0
PASS
```

The ring is bit-exact.

## 5. Real devices through the chain

Patch: `[vst~ Out] 鈫?[amxd~ device] 鈫?[vst~ In] 鈫?[*~ 0.] 鈫?[dac~]`.

| device | result |
|---|---|
| `鈥?Misc/Max Devices/Max Audio Effect.amxd` | 4096 frames back, 0 underruns |
| `鈥?Max for Live/patchers/Max Audio Effect/Autotuna.amxd` | 5120 frames back |

## 6. Patch generated by the plugin itself

`M4LBPatchGen.exe` (same `buildPatch()` the VST3 calls) with the Max Audio
Effect device:

```
out ring fill: 6144 (heartbeat=192, underruns=32)
ramp at 0; compared 4096 frames: mismatches=0 maxDiff=0
PASS
```

So the exact patch the plugin writes into `%TEMP%\M4LBridge\*.maxpat` runs
correctly.

## 7. The bridge VST3 loads and spawns Max

`[vst~ "鈥?M4L Bridge.vst3"]` + `open` inside Max: editor window `M4L Bridge`
appears.

With `M4LBRIDGE_DEBUG=1` and `M4LBRIDGE_DEVICE=<device>`:

```
prepareToPlay sr=44100 device=鈥?Max Audio Effect.amxd
startMaxSide device=鈥?maxExe=F:\Max\MaxRT_nocef.exe
max exe=F:\Max\MaxRT_nocef.exe
patch=C:\Users\asus\AppData\Local\Temp\M4LBridge\m4lbridge_1795257475173.maxpat
spawned max pid=11620
```

The child exited immediately **because the host was Max itself** and Max is
single-instance. This is an artefact of testing the bridge inside Max; FL
Studio does not run Max, so the normal path is unaffected.

## Not yet verified

* loading the plugin inside FL Studio and hearing audio
* MIDI (notes) through the bridge
* parameter mirroring / automation (P1)
* clock drift over long sessions
* the standalone build (it exits immediately in this remote session, likely
  because no audio device is available to it)

## Environment note

In this remote session Max's audio engine ran well below real time (roughly
20鈥?6 % of real time depending on driver), which makes the ring underrun
constantly. That is a property of the session, not of the bridge: the transport
tests above are clock-rate independent and still pass bit-exact.
